# 備考・DMリンクの正本一本化(共通マスター切替)設計

## 目標
顧客備考(1欄)とXのDMリンク(1件)の正本を共通Person(`rpPersons`)に一本化する。店舗アプリの注文・来店・会計・メニュー機能は変更しない。切替前の既存値は失わない。既存Firestore文書は削除しない。

## 仕組み
```
        ┌────────────── 共通顧客マスター rp* (pixies-diner 内の新コレクション・第一候補) ─────────────┐
        │  rpPersons.customerNote / xDmUrl  = 唯一の正本     rpMigrationBatches/cutover = 切替フラグ    │
        └───────▲───────────────────────▲───────────────────────────▲─────────────────────────────────┘
                │ 読み書き(トランザクション)│ 読み書き                    │ 読み書き
        総合DBポータル             ダイナー(連携版)                 常若亭(連携版)
                                   bridge/bridge.js                  bridge/bridge.js (+master-config.js)
                                   店舗の旧フィールドは凍結(読むだけ/書かない/消さない)
```
- **切替フラグ** `rpMigrationBatches/cutover`: `dinerMode` / `tokoMode` = `off`(従来) | `master`。ポータルの「切替」画面から、**切替前チェックが全て合格した場合のみ** `master` にできる。`off` へはいつでも戻せる。
- **連携版アプリ**: 保存版ソースに `store-patches/apply.mjs` で差分を当てた別フォルダを生成(元ソースは変更しない)。フラグが `master` でない、またはブリッジの読込/フラグ取得に失敗した場合は**従来と全く同じ動作**(隔離E2Eで確認)。旧版のままのタブ/アプリもそのまま動く(ただし旧フィールドを編集すると共通との差異として検出される)。

## ダイナー連携版で変わること(masterのときだけ)
| 箇所 | 変更 | 目的 |
|---|---|---|
| 顧客一覧の読込 | 確定リンクのある顧客の `xDmUrl`/`customerNote` を共通Personの値で上書き表示 | 表示の一本化 |
| `customerPayload` | `xDmUrl`/`customerNote` を店舗側へ書かない | 旧フィールド凍結(削除・上書きなし) |
| `saveCustomerCloud`/`saveVisitCloud`/`submitBatchVisits` | 保存前に共通Personへトランザクション保存+変更履歴(ポータルから取り消し可)。一括取込は空で既存値を消さない。未連携の新規客は**独立Person**を作成(同名でも既存人物へ自動統合しない) | 正本への書込み |
| `reconcileNoXVerCounts` / `visitVerCounted` / `visitEditEligibility` | **「フラグを読めた かつ 一度もmasterにしていない」場合だけ従来動作**。master中・master経験後にoffへ戻した場合・フラグ読込失敗/ブリッジ読込失敗では、過去Verを現在のDM有無で書き換え・再計算しない(過去来店の金額修正でも判定は維持) | **過去Verを現在のDMで再判定する既知の危険を停止**。master中は店舗側の旧DMが凍結で古くなるため、off復帰後も安全側に固定。新規来店の判定ルール(DMありで♥)は従来どおり |
| 共通への保存に失敗したとき | 顧客情報の保存は中止して理由を通知(接続エラー状態にはしない)。来店記帳・一括取込は続行し通知のみ | 連携障害で営業を止めない |
| 名前変更(統合でない) | 共通のキャラ名を改名として更新(旧名保持)。店舗側の旧名と共通の現在名が違えば拒否 | 名前の食い違いを残さない |
| 同じ顧客IDでも共通側のキャラ名と違う名前 | 共通へは書かない | 同名別人・ID再利用の誤接続防止 |
| 名前変更で既存顧客へ統合 | 停止し、総合DBの「人物の統合」へ誘導 | 名前一致だけでの自動統合を防ぐ |
| 最後の来店削除の警告文 | 共通の備考/DMは残る旨を表示 | 実態に合わせた説明 |
## 常若亭連携版で変わること(masterのときだけ)
- 確定リンクのあるプロフィール: 備考欄は共通備考。切替前の店舗内旧備考は**参照専用**で併記(自動取り込みなし)。保存は共通Personへ。
- 照合未確認(候補/保留)や未登録のプロフィール: 従来どおり店舗内に保存(画面に「照合未確認: 共通備考には未接続」と明示)。**名前が同じだけで共通備考に接続しない**。照合を確定すると接続される。
- 常若亭は共通マスター用に**もう1つのFirebaseアプリ(pixies-diner)へ匿名ログイン**する(認証方式は現行と同じ匿名。要実機確認)。

## 切替前チェック(`core/cutover.js`)
ダイナー: SourceLink重複なし/確定リンクの参照先あり/**全顧客が確定リンク済み**/**店舗側と共通の備考・DMに差異なし**(差異は「ダイナー側の値を共通へ取り込む」で解消。共通を維持する場合は取り込まず、先に値を揃える)。
常若亭: SourceLink重複なし/全プロフィールにSourceLinkあり(未確認の件数は警告表示)。

## 手順(本番では承認後のみ)
1. 実バックアップの隔離復元PASS(Gate0)・現行Hosting差分確認(Gate1)。
2. ポータルを共通マスターに接続し、`移行`を適用(既存文書は上書きしない)。同名候補を1件ずつ確認。
3. ポータル「切替」で再スキャン→差異を取り込み→チェック合格を確認。
4. `store-patches/apply.mjs` で連携版を生成し、**隔離環境(`npm run test:isolated`)で通す**。
5. 連携版をステージング相当(別サイト)で確認後、本番へデプロイ(別承認)。この時点ではフラグは `off`。
6. フラグを `master` に。問題があれば `off`(共通への書込済みの変更はポータルの「切替」画面の差異として見える)。
## 戻し方と限界
- `off` に戻すと店舗は旧フィールド(凍結時点の値)を表示する。master期間中に共通へ入った変更は店舗側に反映されない(ポータルの差異表示で確認し、必要なら手で戻す)。**自動の書き戻しはしない**(上書き事故防止)。
- 2人が同時に同じ人物の同じ欄を数秒以内に編集した場合の後勝ちは防げない(トランザクションでの破損防止と変更履歴での取り消しのみ)。
- ダイナー内の旧「統合」機能は master 中は止まる(総合DBで統合)。
- **master経験後にoffへ戻しても、連携版は過去Verの再判定を再開しない**(安全側に固定)。従来どおりの再判定を使いたい場合は、店舗側の旧DMを共通と一致させてから従来版を再配信する。
- 連携版の起動時、フラグ/共通マスターの読込に失敗した場合も、再判定は止まり従来表示(旧フィールド)で動く。
- 常若亭で他者が共通備考を更新すると画面が再描画され、入力途中の備考が消えることがある(常若亭の全再描画仕様。保存前に更新しない運用)。
- ダイナー既存の注意: 改名で旧名を別人が再登録すると同じ顧客ID(名前由来)になり得る(従来からの仕様)。連携版は共通側のキャラ名と一致しない書込みを拒否する。
- CSV移行/DM照合修正の機能(`runMigration`/`runReconciliation`)は、master中は備考/DMを店舗側に保存しない(取り込み用途では使わない)。
