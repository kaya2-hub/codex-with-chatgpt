## 実装内容
1. **ChatGPT連携の共通基盤**(イベント・セレモニー共通): `core/exchange.js`(厳格な検証・書き出し・3者比較の差分・適用)、`core/exchange-store.js`(プレビュー→明示確認→保存)、`core/exchange-spec.js`(コピー用仕様書)、`web/ui-docs.js`(画面部品)。外部APIは使用なし。
   - 「ChatGPTで作成/編集」ボタン: **仕様書をコピー**、**編集用データをコピー(仕様書＋現在のデータ)**、**JSONを書き出す(ファイル)**、**JSONファイル/貼り付けの取り込み**(検証→プレビュー→差分を選んで反映)。
   - 新規/更新を区別。更新は項目単位の差分(追加・変更・削除・並べ替え)。他の人の編集と両方が変えた箇所だけ「競合」として利用者が選択。取り込み先の取り違え(別イベントのJSON等)は拒否。
2. **手動編集も正式機能**: 基本情報(名前/店舗/日付/時間/会場/概要/企画/振り返り)、タイムラインの各ステップ(時刻・区切り・かや/合図/トーシンの各項目・追加/削除/並べ替え)、マクロ(追加/編集/削除/コピー)、担当・資料、準備・注意、セレモニー原稿(呼称/内容/感謝コメント/実施後メモ)。**編集は「その1項目だけ」を保存**し、他は変わらない。同時編集は項目ハッシュで検出し、競合時は「最新を読み直す/自分の内容で上書き」を選べる。
3. **タイムライン v2**: 1ステップに時刻の原文表現(「22:55頃」「23時になったら」)・区切り・かや/合図/トーシンの複数項目。項目種別は セリフ/動作/キャラチェンジ/進行条件/演出意図/未分類。旧形式(ルールベース3列・未分類)は閲覧時に自動変換し、保存時は元を `timelineLegacy` に退避。
4. **担当者表記**: 画面は「かや」「トーシン」に統一。内部IDは `Kaya`/`Toushin` のまま、英日どちらの表記でも同一人物(`core/roles.js`)。
5. **マクロUI**: かや/トーシンのグループ、各マクロを個別に折り畳み。コピー・編集・削除はタイトル行に常時表示。15行超は警告のみ。
6. **セレモニー**: 達成(7スタンプごと・確定仕様)×お客様ごとに「セレモニー原稿」を作成(ChatGPT/手動)。**原稿の完成と実施済みは別管理**(取り込みでも完成にならず、完成にしても実施済みにならない)。facts(来店回数・Ver・演目・実施状況)は参照用で取り込み時は無視。個人備考・DM URLはChatGPTへ渡さない。ダーツ抽選・演目状態・実施履歴は既存のまま。
7. **顧客一覧**: 顧客名/店舗/総合来店回数/XのDM(リンク or DMなし)/Verスタンプ(`14(0/7・到達2回分)`形式)。未確認候補は合算せず、読込失敗は「読込失敗」と表示(0回にしない)。
8. **旧機能の整理**: 「Notion/テキスト一括取り込み(貼り付け)」「ルールベース自由文の3列自動分類」を撤去(`core/notion-paste.js` 削除)。旧データは削除せず変換して閲覧/編集可。「仮設定」表記を修正。
9. **その他**: エミュレータ統合テストが正常終了しない問題(Firestore接続の閉じ忘れ)を修正(テスト後に必ず接続を閉じる)。Linuxで `npm run test:emu` が約25秒で終了コード0。

## 採用したJSONスキーマ
`docs/CHATGPT_EXCHANGE.md` に全項目の表あり。要約: `{schema:"ff14rp.event"|"ff14rp.ceremony", version:1, op:"create"|"update", target, _base, event|ceremony:{…}}`。省略した項目は更新されない。配列項目は `id` 付きで、指定すれば全体置換(IDで対応・無いIDは新規・外したものは削除)。`_base` は書き出し時の各項目のハッシュ(ChatGPTには変更させず返してもらう)。未知バージョン・種別違い・必須欠落・型/日付/担当者/項目種別/ID重複・`steps`省略・壊れた`_base`は、保存せず場所(例 `event.timeline.steps[2].kaya[0].type`)を表示して拒否。

## ChatGPT用仕様書(イベント版の冒頭。全文は `docs/samples/chatgpt-spec-event.md` / `…-ceremony.md`)
```
# 役割
あなたは「FF14 RP店舗の総合DB」へ取り込むための“構造化データ”を、利用者(かやさん・トーシンさん)と相談しながら作るアシスタントです。
企画の相談は普段どおり自由な文章で構いません。最終的に、このあと説明する形式のJSONに整理して渡してください。

# 会話のルール
1. 企画の途中は、普段どおり会話してください。JSONは出さなくて構いません。
2. 重要な点(日付・時刻・担当・セリフ・順序)が曖昧なときは、推測せず利用者へ質問してください。
3. 利用者が「これでOK」「書き出して」などと言うまでは、完成データを出力しないでください。
4. 未定の事項は、無理に決めず null または空にして構いません(下書きとして取り込めます)。勝手に補完・創作しないでください。
5. 出力するときは、JSON以外の説明文をJSONの中に混ぜないでください。

# 出力のルール
- ファイルを作成できる環境では、拡張子 .json のファイルとして出力してください(文字コードはUTF-8)。
- ファイルを作成できない環境では、コピーしやすいように```json で囲んだJSON本文を1つだけ出力してください。
- JSONは厳密な形式(コメント・末尾カンマ・省略記号なし)にしてください。
- セリフ・マクロの原文は、要約・言い換え・補正をせず、利用者が書いたとおりに入れてください。改行は \n で表します。
- 担当者は次のどちらかで指定してください(日本語でも内部IDでも可)。
- かや(内部ID: Kaya)
- トーシン(内部ID: Toushin)

# タイムライン(timeline.steps)の作り方
- 画面は「かや | タイミング・合図・共通条件 | トーシン」の3列です。1つの時刻(ステップ)に、複数の行動やセリフを入れられます。
- time: 時刻の原文表現をそのまま入れます。例「22:00」「22:55頃」「23時になったら」。時刻が不明なら空文字 ""。時刻を推測で作らないでください。
- cue: 共通の合図・進行条件・演出意図(中央の列)。kaya / toushin: それぞれの担当の行動とセリフ(左・右の列)。
- 列の中の1項目は {"type": 種別, "text": 原文} です。複数行の文章は text の中で \n を使います。種別:
- "say" = セリフ
- "action" = 動作
- "change" = キャラチェンジ
- "condition" = 進行条件
- "intent" = 演出意図
- "text" = 未分類
- セリフ(say)は原文のまま。行動(action)・キャラチェンジ(change)・進行条件(condition)・演出意図(intent)を区別して書いてください。どれか判断できない文章は "text"(未分類)にしてください。
- 掛け合いは、時系列に沿ってステップを分け、かや・トーシンの列に交互に入れてください。
- 「的な」「みたいな」など確定していない文言は、確定文言として扱わず、そのことが分かるように書いてください(textに注記、または note に記載)。
- phase は「1F祝賀パーティー」「移動案内」などの区切りの名前(任意)です。

# マクロ(macros)の作り方
- body にはFF14のマクロ原文をそのまま入れます(/yell /s /p /wait などのコマンド、改行、空白、記号、<t> などの特殊表記を変更しない)。
- 1つのマクロは15行以内が目安です。超える場合は分割を提案してください(勝手に削らない)。
- 原文が提示されていないマクロを、あなたが創作して作ってはいけません。必要なら利用者に質問し、無ければ登録しないでください。

# 更新(op が "update")のルール
- 利用者から「現在のデータ」(JSON)が渡されたときは、そのJSONを元に、依頼された変更だけを反映した完全なJSONを返してください。
- 既存の項目の "id" は絶対に変更しないでください。新しく追加する項目には "id" を付けないでください(総合DBが付けます)。削除する項目は配列から外してください。
- "_base" は触らずそのまま残してください(二人が別々に編集した際の衝突検出に使われます)。変更しない項目も、元のまま残してください。
- 配列の中の1つの項目(ステップ・マクロなど)は、省略した部分が空として扱われます。既存の項目を更新するときは、元のデータの項目をまるごと(変更しない部分も含めて)返してください。
- 新しく追加する項目の id は、付けないでください(総合DBが付けます)。
- 取り込み前に、利用者は総合DB上で変更差分を確認します。

# 絶対にしてはいけないこと
- "facts"(読み取り専用の情報)・来店回数・Verスタンプ・実施状況・開催状態(下書き/開催済みなど)を変更したり、JSONで指示したりしないこと。これらは総合DBが管理します。
- 個人的な備考・DMのURLなど、資料にない個人情報を作らない・書かないこと。
- 不確かな情報を事実として書かないこと。
…(以降: このデータの種類・スキーマ・記入例)
```

## 未解決事項・制約
- ChatGPTが出すJSONの品質は仕様書と会話に依存(検証とプレビューで不正は止めるが、内容の正しさは人が確認)。
- 配列内の項目の中で省略した部分は「空」になる(仕様書で「既存項目はまるごと返す」と指示。差分プレビューで確認可)。
- `_base` を消す/壊した場合は衝突検出ができない(その旨を表示。ベースなしの削除は既定でオフ)。
- 二人が同じ項目を数秒以内に別々に保存した場合の後勝ちはhash検出の範囲外(競合は次の保存で検出)。
- 旧マクロの `role` が未知の値のときは保持される(選択肢に「旧データの担当」として表示)。
- 「イベントマスター」「GG等テンプレート({変数}置換)」は旧方式のまま共存(今回は撤去せず)。
- Notion自動取り込み・外部API連携は対象外(ChatGPT経由のJSONに一本化)。
